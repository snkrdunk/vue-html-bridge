# `@vue-html-bridge/adapter-markuplint` Design

Status: Proposed  
Package directory: `packages/adapter-markuplint`

## 1. Role

This is the initial standard adapter that connects [Markuplint](https://markuplint.dev/) to `@vue-html-bridge/validator-api` v1.

### In scope

- In-memory HTML validation using the Markuplint Node API
- Discovering and loading Markuplint config, and managing engine lifecycle
- Always validating the generated HTML through an HTML parser
- Converting violations (message/rule/severity/range) into the common format
- Converting Markuplint-specific locations to UTF-16 offsets
- Converting config/engine failures into `AdapterFailure`

### Out of scope

- Parsing Vue SFCs
- Passing an SFC directly to the Markuplint Vue parser
- Converting generated ranges into SFC source ranges
- Cross-variant aggregation, LSP diagnostics, hover
- `--fix` or modifying the source

## 2. Public API

```ts
import type { HtmlValidatorAdapter } from "@vue-html-bridge/validator-api";

export interface MarkuplintAdapterSettings {
  /** If given explicitly, resolved from workspaceRoot. */
  configFile?: string;

  /** If configFile is not set, search upward from sourceFilename. */
  searchConfig?: boolean; // default: true

  /** Adjusts source-style rules that do not fit HTML generated by the bridge. */
  profile?: "generated-html" | "as-configured"; // default: generated-html

  /**
   * Per-rule overrides applied after the generated-html profile overlay.
   * Lets you re-enable a specific rule that the overlay disabled.
   */
  profileRuleOverrides?: Readonly<Record<string, boolean>>;

  locale?: string;
}

export const markuplintAdapter: HtmlValidatorAdapter<MarkuplintAdapterSettings>;
```

Adapter metadata:

```ts
{
  apiVersion: 1,
  id: "markuplint",
  displayName: "Markuplint",
  capabilities: {
    execution: "in-process",
    supportsCancellation: false,
    supportsConfigFiles: true,
    fragmentHandling: "native",
    maxConcurrentValidations: 1,
    configFilePatterns: [
      "**/.markuplintrc",
      "**/.markuplintrc.*",
      "**/markuplint.config.*",
      "**/package.json"
    ]
  }
}
```

`maxConcurrentValidations: 1` is a conservative initial value, because we have not yet confirmed the engine is safe to run concurrently. We will consider raising it once the engine-reuse spike (§3.1) gives us results. `configFilePatterns` must stay in sync with the config search targets of the supported Markuplint version. This synchronization is not maintained by hand: the config-search filename list of the supported Markuplint version is recorded as a source-controlled fixture during the Phase 0 spike (§3.1 item 7), and a drift test fails when a Markuplint update changes the search targets or when `configFilePatterns` no longer matches the fixture (§9.2 item 14).

`supportsCancellation: false` applies as long as the Markuplint engine does not accept a native `AbortSignal`. The adapter checks the signal before and after execution, and the analyzer discards stale results.

## 3. Using the Markuplint API

Markuplint offers a public Node API: `MLEngine`, `exec()`, `configFile` / `config` / `noSearchConfig`, and so on. We use the ESM Node API, not the CLI process or the JSON formatter.

```ts
import { MLEngine } from "markuplint";

// Conceptual code. How to build an MLFile in memory
// will be fixed in Phase 0, against the public API of the target Markuplint version.
const file = await createInMemoryMlFile({
  sourceCode: request.html,
  filename: request.virtualFilename,
  parser: "html",
});

const engine = new MLEngine(file, {
  configFile: resolvedConfigFile,
  noSearchConfig: true,
  fix: false,
  locale: settings.locale,
});

const result = await engine.exec();
```

### 3.1 Acceptance criteria for the technical spike

Before we pin a Markuplint version, we must confirm the following with real code:

1. We can validate an HTML string without writing it to the filesystem, using an arbitrary `.html` virtual filename.
2. `extends`, plugins, `rules`, and `nodeRules` in an explicit config file resolve correctly.
3. Vue parser mappings in the config do not apply to the virtual `.html`, even if present.
4. We can determine exactly which substring of the generated HTML a violation points to — the unit, base, and end semantics of line/col/raw.
5. We measure which layer (engine or file) can be reused across calls with the same config. We also confirm whether concurrent `validate` calls are safe, and use that to decide the value of `maxConcurrentValidations`.
6. We fix the first version of the generated-html profile's rule manifest, based on the rule list of the target Markuplint major version.
7. We record the config-search filename list of the target Markuplint version as a source-controlled fixture. `configFilePatterns` (§2) is asserted against this fixture, so a version update that adds or removes a search target fails a test instead of drifting silently.

Only if the public API cannot satisfy item 1, we consider a temporary-file fallback inside the adapter. Even then, it must use a safe OS temp directory, a filename that does not collide across variants, and `finally` cleanup — and must not leak temp files to the analyzer/core. We will not parse human-readable CLI stdout.

### 3.2 Module format

Because Markuplint itself is ESM, this package and the language server build will target ESM as the first choice. We avoid depending on `@markuplint/esm-adapter` for CommonJS. The supported Node/Markuplint versions are documented as peer dependencies and in the CI matrix.

## 4. Config resolution

Markuplint's config search and its parser/override matching both use the same "filename" concept, and that creates a conflict here.

- Config should follow the same project settings as the original SFC.
- But the input should be parsed as the already-generated HTML, not as the Vue SFC.

To resolve this, we split the process into two steps:

1. Search for the nearest Markuplint config starting from the directory of `sourceFilename`.
2. Pass the found config path explicitly to `MLEngine`, and use the `.html` `virtualFilename` as the lint target identity.

We set `noSearchConfig: true` so Markuplint does not re-search starting from a directory that does not actually contain the virtual filename.

### 4.1 Search order

1. `settings.configFile`
2. If `settings.searchConfig !== false`, search upward from the source directory for config filenames that Markuplint supports
3. Markuplint's default/recommended config

If an explicit config is missing or fails to parse, we report `configuration-error` and do not silently fall back to the default. We only use the default when auto-search finds nothing.

### 4.2 Filename used for overrides/parser/exclude

`overrides`, `parser`, and `excludeFiles` in the config are evaluated against `virtualFilename`. This means `.vue`-targeted overrides and `@markuplint/vue-parser` do not apply to the generated HTML. This is intentional.

If you want to write a bridge-specific override, match it against the synthetic suffix:

```json
{
  "overrides": {
    "**/*.vue.__vue_html_bridge__/**/*.html": {
      "rules": {
        "some-source-format-rule": false
      }
    }
  }
}
```

The format of the synthetic path is defined as a public contract in `@vue-html-bridge/validator-api` §3.2, and will not change in a breaking way.

### 4.3 Config cache

The session caches the config path and the identity of dependent configs/plugins. Config changes are not detected by an adapter-specific watcher; instead, we unify detection so the language server watches the `configFilePatterns` capability. On change, the language server calls `reconfigure({ invalidateAdapters: ["markuplint"] })`, which recreates the whole session — and any validation cache tied to that session is also dropped (analyzer.md §10.2 and §11). Because `configFilePatterns` only covers known config-file candidates, changes to arbitrarily-named local `extends` targets or plugin implementations are not detected, and do not take effect until the next session recreation.

## 5. Generated HTML profile

The output of core does not reproduce source formatting, and converts events such as `@click` into things like `onclick="dummy-fn"`. Because of this, applying rules that only make sense for hand-written source would produce false positives against constructs the bridge itself created.

`profile: "generated-html"` applies a small config overlay managed by the adapter.

- Disables rules that only check source formatting, such as indentation, quote style, and attribute order.
- Disables, by default, rules that treat a component fragment as a full document, such as requiring `html` / `head` / `meta`.
- Keeps rules for HTML content model, attribute values, ARIA, ID references, and accessibility semantics.

An `onclick="dummy-fn"` generated from `@click` cannot be distinguished from an `onclick` that genuinely exists in the source, just by looking at the HTML string. Because of this, we do not blanket-disable rules like `no-use-event-handler-attr` in the adapter profile. Instead, the adapter still returns the violation, tagged with `applicability: "source-representation"`. The analyzer then looks at core's provenance data and suppresses the violation only when it originates from a synthetic Vue event. The mapping from rule ID to applicability stays internal to the Markuplint adapter.

Rules like `aria-controls` / `for`, which may reference an ID outside the fragment, depend on the host context, so we cannot always judge a missing reference without false positives. How each such rule is treated by the profile is documented in the rule manifest. If we enable it strictly, we show in hover/documentation that the meaning is "no reference target inside the current SFC fragment."

The exact rule list is kept as a source-controlled manifest per supported Markuplint major version, and must not grow or shrink implicitly. When a rule set explicitly by config conflicts with the profile, we apply this priority order:

```text
Markuplint defaults < discovered/user config < generated-html safety overlay
  < settings.profileRuleOverrides
```

Use `profileRuleOverrides` to bring back a specific rule that the overlay disabled. If you want no overlay at all, choose `profile: "as-configured"` (this validates strictly according to config, including the serializer's output). Which rule the profile changed, and why, can always be looked up in the rule manifest.

Finalizing the first version of the rule manifest is an acceptance criterion for Phase 0; we do not move on to the Phase 1 vertical slice until it is finalized (monorepo.md §14). Which HTML/ARIA/accessibility rules run by default is itself product behavior, so we do not defer it as a mere implementation detail.

## 6. Converting violations

Conceptually, the conversion looks like this:

```ts
function toGeneratedDiagnostic(
  html: string,
  violation: MarkuplintViolation,
): GeneratedDiagnostic {
  return {
    ruleId: violation.ruleId,
    severity: toSeverity(violation.severity),
    message: violation.message,
    range: toUtf16Range(html, violation),
    applicability: classifyApplicability(violation.ruleId),
    fingerprint: stableViolationFingerprint(violation),
  };
}
```

### 6.1 Range

- We pin down the line/column base and the character unit of a Markuplint violation using fixtures for the supported version.
- We build a line-start index from `html` once, and convert line/column into a UTF-16 absolute offset.
- When `raw` or a length is available, we confirm that substring matches `html.slice(start, end)`.
- If no end is available, we use the token/raw length. If nothing is available, we use a zero-width range or `undefined`, and never widen it to an unrelated HTML token.
- Core's output follows a single-line contract, but the adapter contract and its unit tests also support multi-line HTML. This is so the adapter keeps working correctly with a future wrapper, or when used standalone.
- Fixtures include CRLF, emoji, and combining characters.

If we find that Markuplint's coordinates are not UTF-16, we build a dedicated index that converts from code point/byte to UTF-16. We never use a plain `lineStart + col` without justification.

### 6.2 Severity/code URL

We map Markuplint severities to `error` / `warning` / `info`. Unknown severities are downgraded to warning, and we log this on the adapter side. We attach `codeDescriptionHref` only when we can build a stable URL for the rule documentation.

### 6.3 When the result is null

When `exec()` returns `null` — for example, because of ignore/exclude — we distinguish the reason:

- Excluded by config: no diagnostics, with the ignored reason recorded in metadata
- The engine could not produce a result: report `invalid-validator-result` as a failure

We do not conflate silent success with an engine error.

## 7. Failure and safety

| Event on the Markuplint side      | Adapter result                                                                                       |
| --------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Config file missing / parse error | `configuration-error`                                                                                |
| Plugin/parser import failure      | `configuration-error`                                                                                |
| Markuplint package/API mismatch   | `validator-unavailable`                                                                              |
| `exec()` throws                   | `execution-error`                                                                                    |
| Violation shape/range is invalid  | Returns whatever violations are usable, and also returns `invalid-validator-result`                  |
| Abort                             | AbortError before execution starts. AbortError after execution completes, if it was already running. |

Error messages are a user-actionable summary. We do not include stack traces, absolute temp paths, or environment variables in `AdapterFailure.details`.

Markuplint plugins/config can run arbitrary code from the workspace. The adapter itself does not judge trust, but we document the contract that the language server only creates a session for a trusted workspace.

## 8. Performance

- Config resolution and module loading are shared within a session.
- The HTML content hash cache lives in the analyzer, so the adapter does not keep a duplicate cache.
- We will measure whether the Markuplint engine needs to be created per input. If reuse mixes in mutable state, we prioritize safety over reuse.
- We do not use watch mode in the initial version, because it would create a second watcher alongside the LSP lifecycle.
- We always pass `fix: false`.

## 9. Testing

### 9.1 Contract suite

We run the full contract test suite from `@vue-html-bridge/adapter-testkit` against the real adapter.

### 9.2 Markuplint-specific fixtures

1. Priority between config auto-discovery and an explicit config.
2. Resolution of `extends`, plugins, `rules`, and `nodeRules`.
3. The virtual `.html` is parsed as HTML even when a `.vue` parser setting exists.
4. The bridge synthetic-path override applies correctly.
5. Rule, severity, and range for HTML/ARIA/content-model violations.
6. Deterministic ordering when the same markup has multiple violations.
7. Positions with emoji, CRLF, multiple lines, and attribute name/value/end tag.
8. Fallback contract for violations without a range.
9. The generated-html profile removes source-format false positives while keeping semantic rules.
10. Failure classification for config/plugin errors versus engine throws.
11. Behavior before abort / during execution / immediately after completion.
12. Session dispose and reconfigure.
13. Detecting API shape across the Markuplint major/version matrix.
14. `configFilePatterns` matches the config-search filename fixture recorded for the pinned Markuplint version (§3.1 item 7); the test fails on drift when the version is updated.

### 9.3 Golden tests

We save both the raw Markuplint violation and the normalized result as fixtures. However, to avoid a large batch of fixture updates from a minor change in Markuplint's full message text alone, we separate structural assertions (rule/range/severity) from assertions on only the important part of the message.

## 10. Open questions

Each item notes where the decision will be made.

- The best public API for passing a source string plus virtual filename to `MLEngine` (Phase 0 spike, §3.1)
- Whether a generated file excluded by config's `excludeFiles` should be a silent ignore or an info diagnostic (decided during Phase 1 implementation)
- Capability update once Markuplint offers native cancellation (once upstream supports it)
- Config dependency watcher: the initial version already unifies on the language server watching `configFilePatterns`. Whether an adapter-specific watcher is needed will be reconsidered if dependencies outside the watch target (e.g., `extends` inside `node_modules`) cause real problems (an ADR after measurement)
